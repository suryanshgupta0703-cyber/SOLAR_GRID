1. PROJECT OVERVIEW & FINAL REVIEW OBJECTIVES
================================================================================
SolarGrid is an autonomous artificial intelligence microgrid management system
engineered to solve the intermittency and economic mismatch ("The Duck Curve")
inherent to residential and institutional rooftop solar photovoltaic (PV) systems.

In typical residential communities, peak solar generation occurs during midday
(10:00 AM - 3:00 PM), while peak human electricity consumption occurs during
morning hours (7:00 AM - 9:30 AM) and evening hours (6:30 PM - 10:30 PM).
Uncoordinated operations lead to solar curtailment or low-value grid feed-in
(Rs 2.50/kWh), while heavy loads draw expensive peak grid power (Rs 8.50/kWh).

SolarGrid solves this by:
1. Forecasting 24-hour generation and community demand using an LSTM + XGBoost
   hybrid ensemble model.
2. Ingesting real-time weather and Global Tilted Irradiance (GTI) via the
   Open-Meteo Forecast API without requiring expensive IoT sensors.
3. Automatically scheduling flexible heavy community loads (EV charging fleet,
   community water pumps, HVAC pre-cooling) into solar surplus hours using a
   Greedy Priority Bin-Packing heuristic.
4. Enforcing strict non-interruptible blocks, operating deadlines, and an
   adjustable transformer safety threshold (20-60 kW, default 35 kW).
5. Letting operators interactively model their own appliance fleet: number of
   units, per-unit kW rating, run-duration, and transformer cap. Each unit is
   scheduled as an independent instance so loads interleave across surplus hours.
6. Providing full economic (Rupee savings) and ESG (CO2 mitigated and mature
   trees planted) ledgers in a production-ready Streamlit dashboard.

3. METEOROLOGICAL MODELING, SQLITE PERSISTENCE & REAL-DATA INGESTION
================================================================================
3.1 Synthetic Physics Engine & Weather Variables (data_gen.py):
Constructed using empirical solar geometry equations for offline benchmarking
(fixed random seed 42; 30 days x 24 hours = 720 records from 2024-01-01):
- Clear-Sky Irradiance (I_cs): Sinusoidal diurnal arc peaking at solar noon:
  I_cs(t) = max(0, 1000 * sin(pi * (t - 6) / 12))  [W/m2]
- Cloud Attenuation (Beer-Lambert approximation): cloud cover reduces incoming
  radiation via a transmittance factor, with small Gaussian noise.
- Photovoltaic Power Output (P_solar): System capacity (50 kW peak),
  temperature derating (-0.4%/deg C above 25 deg C), and inverter/system loss (95%):
  P_solar(t) = P_rated * (I_actual / 1000) * [1 - 0.004 * (T - 25)] * 0.95

3.2 Dual-Peak Community Demand Modeling:
Superposed Gaussian behavioral lobes representing residential habits:
- Morning Peak (07:00 - 09:30): Water heating, cooking, breakfast prep.
- Midday Valley (11:00 - 16:00): Low residential occupancy (10-14 kW base load).
- Evening Peak (18:30 - 22:30): HVAC, lighting, entertainment, dining.
- Community peak demand scale: ~45 kW (representative ~20-home community).

3.3 Relational SQLite Database Architecture (solargrid.db):
- Mode: Write-Ahead Logging (WAL) for high-concurrency read operations.
- DB path resolved relative to the module so the app runs from any cwd.
- Table `historical_energy`: 720 records spanning 30 consecutive days.
  Columns: timestamp, temperature_c, cloud_cover_pct, solar_irradiance_wm2,
           historical_solar_gen_kw, historical_baseline_demand_kw.
- Table `forecasts`: Serialized 24-hour model output history (optional/future use).

3.4 Real-Data Layer: Open-Meteo Forecast API (data_fetcher.py):
To address guide feedback regarding synthetic datasets with zero hardware cost:
- Connects to Open-Meteo REST API (100% free, zero authentication keys needed).
- Uses stdlib urllib (no `requests` dependency), 15 s timeout, 3 retries.
- Fetches ONE FULL LOCAL CALENDAR DAY (00:00-23:00) via start_date=end_date and
  timezone=auto, guaranteeing 24 aligned hourly rows.
- Ingests Global Tilted Irradiance (GTI), Direct Normal Irradiance (DNI),
  cloud cover percentage, and ambient 2-meter temperature; interpolates nulls.
- Appends cyclical time features to match the inference feature schema exactly.
- Public functions:
  * fetch_live_forecast(lat, lon, city_name, target_date): real-time day weather.
  * fetch_historical_archive(lat, lon, start, end): real historical weather
    (Archive API; available for dataset regeneration, not used by live mode).
  * CITY_PRESETS: Jammu (32.72 N, 74.85 E), Delhi, Mumbai, Bengaluru, Jaipur, Chennai.
- Graceful fallback: failed live fetches are NOT cached; the app falls back to the
  benchmark synthetic forecast and shows a warning banner (never crashes).

4. MACHINE LEARNING & DEEP LEARNING FORECASTING ENGINE
================================================================================
4.1 Deep Learning Model: PyTorch Stacked LSTM (models/lstm_model.py):
- Input Layer: 8 features (Temp, Clouds, GTI, Hour_sin, Hour_cos, DoW_sin,
  DoW_cos, DayOfYear).
- Architecture: 2 stacked LSTM layers with 64 hidden units each, batch_first,
  dropout 0.20 between recurrent layers.
- Regression Head: take the LAST hidden state (many-to-one) -> Dropout ->
  a single Linear(64 -> 1). (The head is one linear projection, not an MLP.)
- Sequence Lookback: 24 preceding hours (seq_len = 24) to predict hour t.
- Optimizer: Adam (lr = 1e-3). Loss: HuberLoss (robust to outliers vs plain MSE).
- Gradient-norm clipping (max_norm = 1.0); 30 epochs; batch size 32; no shuffle.
- Best-validation-loss weights are checkpointed and restored before saving.
- Inference warm-up: first feature row replicated seq_len times as history.

4.2 Extreme Gradient Boosting: XGBoost Regressor (models/train_models.py):
- Hyperparameters: n_estimators = 300, max_depth = 6, learning_rate = 0.05,
  subsample = 0.8, colsample_bytree = 0.8, tree_method = "hist",
  early_stopping_rounds = 20, eval_metric = "mae", random_state = 42.
- Captures abrupt non-linear optical cutoffs (e.g. cloud shading transitions)
  and temperature-dependent residential cooling load correlations.
- Saved in both joblib and native JSON formats for portable loading.

4.3 Hybrid Ensemble Strategy (models/forecast.py):
Final Solar Prediction:
  Y_hat_solar = 0.55 * Y_hat_LSTM + 0.45 * Y_hat_XGBoost
LSTM enforces diurnal temporal smoothness while XGBoost captures sharp non-linear
cloud step-changes. Outputs clipped to physical bounds (solar 0-55 kW, demand
3-55 kW). Demand Prediction:
  Y_hat_demand = Y_hat_XGBoost_demand (driven by temporal encodings & temperature).
If model artefacts are missing, a physics-only fallback keeps the UI functional.

6. ENERGY BALANCE & SOLAR SURPLUS IDENTIFICATION
================================================================================
Net Energy Balance:
  B(t) = P_solar(t) - P_demand(t),   for t in [0, 23]
Operational Regimes:
1. Surplus Window (B(t) > 0): Typically 10:00 AM to 3:00 PM, generating up to
   +35 kW of net clean energy. Without scheduling, this energy is exported
   at low feed-in tariffs (Rs 2.50/kWh).
2. Deficit Window (B(t) < 0): Morning and evening periods requiring grid draw
   at expensive peak rates (Rs 8.50/kWh).

+-----------------------+------------+----------+----------+---------------+----------+

7.2 Interactive Per-Unit Configuration (Option B: individual instances):
The Smart Scheduler tab exposes a bordered card per category. UI ranges live in
app_v2.py::_APPLIANCE_UI, zipped with DEFAULT_APPLIANCES so model and UI stay aligned:
+---------------------+----------------+----------------+----------------+
| Control             | EV Charger     | Water Pump     | HVAC Zone      |
+---------------------+----------------+----------------+----------------+
| Number of units     | 1-5            | 1-4            | 1-3            |
| Power per unit (kW) | 3.0-22.0       | 1.0-15.0       | 1.0-10.0       |
| (step 0.5)          |                |                |                |
| Run duration (h)    | 1-6            | 1-4            | 1-4            |
+---------------------+----------------+----------------+----------------+
Global slider: Distribution Transformer Limit = 20-60 kW (default 35, step 1).

Expansion logic (_configured_appliances): for each enabled category, ONE Appliance
is created PER UNIT using dataclasses.replace(base, name=..., power_kw=cfg_kw,
duration_hours=cfg_dur). When count > 1 the instances are named "EV Charger #1",
"EV Charger #2", ...; when count = 1 the base name is kept. DEFAULT_APPLIANCES is
never mutated. Each unit is scheduled independently, so units INTERLEAVE into
different surplus hours rather than forming one oversized block.

Shared state (_appliance_settings): values are read from st.session_state because
the Carbon & Savings tab renders BEFORE the Scheduler tab creates its widgets.
Both tabs consume the identical configured list and transformer cap, so they
always agree. A live caption shows the maths, e.g. "2 x 11.0 kW = 22.0 kW".

7.3 Multi-Constraint Greedy Priority Bin-Packing Algorithm:
1. For Non-Interruptible Appliances (EV Charging):
   Scans all candidate contiguous windows of length D before deadline.
   Pass 1: pick the contiguous block fully covered by surplus that maximizes
   solar capture while keeping total load (base demand + power) under the cap.
   Pass 2: if none, pick the cheapest-tariff block that still fits the cap.
2. For Interruptible Appliances (Water Pump, HVAC):
   Ranks individual candidate hours descending by available surplus B(t).
   Greedily allocates hours until duration is satisfied, respecting the cap.
3. After each assignment, update surplus[t] and total_load[t] so later appliances
   see the updated state. Infeasible appliances are reported in `unscheduled`.
4. Fallback Mechanism:
   If solar surplus is exhausted or insufficient (e.g. severe rain/monsoon),
   non-interruptible loads land in the cheapest night off-peak tariff block
   (Rs 4.00/kWh), preventing expensive peak draws.

7.4 Transformer Safety Cap Enforcement & ToD Costing:
- Hard cap peak_cap_kw (20-60 kW, default 35) on base demand + scheduled load per
  hour; offending slots are skipped. The safety badge lists offending hours and
  notes when base demand alone exceeds the cap.
- compute_tod_savings(schedule_result, solar, demand, appliances=None) builds a
  power lookup from the PASSED appliance list, so renamed per-unit instances and
  custom kW ratings are costed correctly. (Passing the configured list fixed a bug
  where looking up DEFAULT_APPLIANCES names returned 0 and zeroed all savings.)
  Baseline = all scheduled energy at peak Rs 8.50; Optimized = sum over scheduled
  hours of power * tariff(hour); Savings = baseline - optimized (+ % reduction).

10. EXECUTION & DEMONSTRATION GUIDE FOR THE EVALUATION COMMITTEE
================================================================================
Step 1: Open a terminal in the project root (the folder containing app.py).

Step 2: Create and activate a Python environment, then install dependencies:
   python3 -m venv .venv
   source .venv/bin/activate        (Windows: .venv\Scripts\activate)
   pip install -r requirements.txt

Step 3: (Optional) Regenerate data and retrain models from scratch:
   python data_gen.py
   python models/train_models.py
   (The repo ships with solargrid.db and trained weights, so this is optional.)

Step 4: Run the automated test suite (10 cases):
   python -m pytest tests/test_scheduler.py -v
   (If a third-party pytest plugin crashes, prefix PYTEST_DISABLE_PLUGIN_AUTOLOAD=1.)

Step 5: Launch the full Phase 1-7 production dashboard:
   streamlit run app.py
   Open http://localhost:8501

Evaluation Committee Navigation:
- Sidebar: Toggle between "Historical Benchmark" and "Live City Forecast".
  Select a city (e.g. Jammu, Bengaluru, Jaipur) to demonstrate live weather
  ingestion without hardware sensors. Switching cities updates every chart/KPI.
- Tabs 1 & 2 (24-Hour Forecast, Surplus Analysis): Inspect predictive curves and
  surplus window identification.
- Tab 3 (Carbon & Savings): Inspect the "Ask SolarGrid" AI summary box, carbon KPI
  cards, and Rupee savings ledger. These reflect the appliance configuration.
- Tab 4 (Smart Scheduler): Use the appliance cards to set number of units, kW per
  unit and run-duration; adjust the transformer limit (20-60 kW). Watch the Gantt
  chart, power-balance chart, safety badge and savings update live. Try EV units=2
  to see EV Charger #1 / #2 interleave into separate surplus hours.
- Tabs 5 & 6 (Data Exploration, Model Architecture & Evaluation): Available in
  Historical Benchmark mode only; review database records, feature correlations,
  and LSTM/XGBoost holdout metrics.

Known UI behaviour (pre-existing, not a calculation error): after changing a
widget, the active tab may reset to the first tab. Settings are preserved; simply
click back to the tab you were on.
